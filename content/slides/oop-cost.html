ราคาของ OOP: ต้นไม้คลาสที่ลึกเกินไป

GameObject
└─ Character
   └─ Ally
      └─ DestructionAlly
         └─ TrailblazerV2

  • แก้ Character ทีเดียว ลูกหลานพังทั้งตระกูล
  • โค้ดยาว มีพิธีเยอะ (boilerplate)

Joe Armstrong (ผู้สร้างภาษา Erlang) เปรียบไว้ว่า อยากได้แค่กล้วยลูกเดียว แต่ได้กอริลลาที่ถือกล้วย พร้อมทั้งป่ามาด้วย

บทเรียนที่วงการได้: ใช้การประกอบ (composition) มากกว่าการสืบทอด — หนังสือ Design Patterns, 1994

ทุกทางแก้มีราคา OOP ก็เช่นกัน ต่อเกม Honkai: Star Rail ของเรา: เกมโตขึ้น ต้นไม้คลาสก็ลึกขึ้นเรื่อย ๆ GameObject → Character → Ally → DestructionAlly → TrailblazerV2 วันหนึ่งทีมอยากให้ตัวละครได้ Energy เพิ่มตอนโดนตี เลยแก้ที่ Character ทีเดียว ปรากฏว่าศัตรูและบอสที่สืบทอดจาก Character ก็ได้ Energy เพิ่มด้วย ปล่อยท่าใหญ่ถี่ขึ้นทั้งเกม แถมบางคลาสที่ไม่รู้ว่ามีอยู่ก็พังด้วย ทำไมชื่อ TrailblazerV2: ตัวเอก (Trailblazer) ในเกมเปลี่ยน Path ได้ ถ้าออกแบบด้วยการสืบทอด ต้องมี DestructionTrailblazer, PreservationTrailblazer, HarmonyTrailblazer … แล้ว object ที่สร้างไปแล้วเปลี่ยน class กลางเกมไม่ได้ สุดท้ายต้องรื้อทำ V2 อีกรอบ — ถ้าใช้การประกอบ แค่สลับชิ้น Path ที่ถืออยู่ก็จบ เรื่องกล้วยกับกอริลลาแบบ Honkai: Star Rail: อยากให้ memosprite (ร่างที่ตัวละครสาย Remembrance เรียกออกมา) มี HP เลยให้สืบทอดจาก Character เพื่อเอาระบบเลือด แต่ได้ช่องใส่ Light Cone, Relic, Eidolon และ Traces ติดมาทั้งก้อน ทั้งที่ memosprite ไม่ได้ใส่ของพวกนี้เอง อยากได้แค่กล้วย แต่ได้กอริลลาพร้อมทั้งป่า บทเรียน composition: แทนที่ “TrailblazerV2 เป็น DestructionAlly เป็น Ally เป็น …” ให้คิดว่า “Ally มี Health มี Path มี LightCone” และ “memosprite ก็มี Health ชิ้นเดียวกัน” คือเอาชิ้นส่วนมาประกอบ เปลี่ยนชิ้นไหนก็ไม่กระทบชิ้นอื่น (เกมเอนจินสมัยใหม่อย่าง Unity และ Unreal ใช้ระบบ component แบบนี้) ภาษารุ่นใหม่อย่าง Go และ Rust ไม่มี class inheritance แบบ Java เลย เป็นผลของบทเรียนนี้
